## Common data and invariants

| Domain | Required information / rule |
| --- | --- |
| Identity | Stable `subscriptionId`, owner account ID, `platformId` when resolved. Never identify records by name; same-platform plans can coexist. User A cannot access user B's IDs. |
| Money | Currency + decimal amount; proposed transport `{ currency: 'USD', amount: '11.99' }`. Decimal-safe server arithmetic, currency precision validation; no floating-point aggregation or cross-currency totals. Adapt legacy `price:number` explicitly. |
| Cycle | `weekly`, `monthly`, `quarterly`, `yearly`; no custom billing cycle. |
| Dates | Billing/start/trial/event dates as `YYYY-MM-DD` in user calendar; IANA timezone on account/snapshot. Audit timestamps UTC. Do not parse calendar dates through UTC midnight to determine local day. |
| Recurrence | Original anchor, cycle, tracking state, schedule version. Month-end clamp from original anchor, not the previous clamped occurrence. Trial-end first charge once; subsequent dates one cycle later. |
| Provenance | Creation source manual/AI/voice/Gmail, creator account email snapshot, originating inbox when applicable, date source (`user`, `confirmed`, `predicted`), source evidence/confidence. Matching new evidence does not erase creation provenance. |
| Lifecycle | Explicit cancellation/access-until and confirmed access expiry separate from contextual date status. Past estimated renewal alone is never Expired. Preserve notes and unrelated source fields through edits. |
| Trial | Duration, start, exact/calculated end, end source/confidence, auto-renew tracking, post-trial money and cycle. A boolean alone is insufficient. See [trials](product-screens.md#tracked-trials). |
| Reminder | Mode `off`, `once`, `daily_last_three`; once offset / custom days, event target, timezone, schedule version. Persist preference separately from send eligibility. |
| Platform | Canonical name/category/aliases, bundled/trusted logo reference, verified HTTPS management links and billing provider. Unknown identity → pending/fallback, never invented assets/links. |
| Event | Stable `eventId`, `subscriptionId`, `eventType` renewal/trial-end, date, `expectedCharge`, money when a charge, confidence, schedule version. Event identity survives recomputation; no duplicate first post-trial charge. |
| Payment | Stable payment ID, subscription + billing-cycle key, paid date, money, confirmation source, evidence identity and confirmation timestamp. One confirmation/cycle; no duplicate totals or schedule advancement on retry. |
| Alert | Actual sent notification ID, subscription/event IDs, sent timestamp, copy/event type and delivery state. Future queued jobs are not Alerts. |

Explicit null means unknown/unset; do not silently substitute today, zero price or an email from a different identity. Distinguish omitted PATCH fields (unchanged) from explicit clearing. Use revision/version checks for concurrent edits; report conflicts without discarding a local draft.

### Status mapping shared by all surfaces

Suggested wire groups map to preview group keys below. A backend may adopt different names only through the shared schema and an explicit adapter; do not expose legacy `upcoming/in_progress/expired` directly as this model.

| Suggested `statusGroup` | Preview key | Display |
| --- | --- | --- |
| `active` | `active` | Active |
| `trial` | `trial` | On trial / Trial ending soon / Trial ends today |
| `trial_ended` | `trial-ended` | Trial ended |
| `renewing_soon` | `renewing-soon` | Renewing soon |
| `due_today` | `due-today` | Due today |
| `needs_date` | `needs-date` | Needs date |
| `cancelled` | `cancelled` | Cancelled |
| `expired` | `expired` | Expired |

One group per record. Explicit Expired/Cancelled override contextual states; ended non-renewing trial → Trial ended; current trial → trial group; then missing date, due today, 1–7 days away, otherwise Active. On the trial end date retain trial wording/event; after it passes auto-renew-On tracking remains active. No state implies Paid. Trial contextual label and payment evidence remain separate fields.

Shared next-seven-day window: **today through today + 7 calendar days inclusive**. Due today is its own group; Renewing soon covers days 1–7. Home upcoming stats include eligible trial ends and renewals. List Active count is a group count, not Home Tracking count.

### Amounts must retain their meaning

- Monthly-equivalent platform spending: normalize cycle, exclude free trials and ended/cancelled/expired plans; aggregate platform within currency.
- This month / forecast: actual scheduled expected charges, including known auto-renewing trial-end charge; not monthly-equivalent cost or payment proof.
- Payments / Profile paid totals: explicit confirmed-payment records only.
- A non-renewing trial end can contribute an event count with no charge. Missing dates cannot produce projected charges.

### Scan, mutation and schedule safety

- Scope candidate IDs to their valid scan owner. Linking temporary owner to account requires verified session/ownership and must be replay safe. Never accept arbitrary inbox email as authorization.
- Batch import, create, receipt application and confirmation need idempotency keys/constraints. A retry returns the original result or a conflict, not duplicate records/jobs/payments.
- Preserve manual corrections on sync. Deduplicate successful receipt identity across inboxes; ambiguous same-platform matches require review/skip. Failed/upcoming invoices are not successful payment evidence.
- Trial/date/auto-renew/reminder changes invalidate Detail/List/Home/Calendar/platform summaries and rebuild pending jobs; sent Alerts remain. Cancelling/deleting prevents stale-worker delivery.
- Ignore stale async responses after route/query/month/account changes. Do not show another account's cached data after logout.
- All v1 features, AI extraction, Gmail initial/repeated/incremental scans and extra inboxes are free, including more than 25 live records/imported selections. Do not gate on `pro`, subscription tier, first-scan usage, store state or a monetization cap. Keep ownership, consent, idempotency and explicit operational limits/errors; no silent drops. [Billing](billing.md#revenuecat) owns Phase 2 only.

## Errors and mobile request states

Agree an envelope with stable error code, user-safe message, optional field errors, retryability, request ID and relevant challenge/conflict/access metadata. Never put passwords, OTPs, tokens or raw mail into logs/error bodies. Map validation under the correct field; distinguish auth expiry, denied inbox scope, scan interruption, no candidates, no payment receipt, offline failure, conflict and operational rate limits; no Pro-required/paywall error in v1.

Every request distinguishes idle/pending/resolved-data/resolved-empty/error. Disable duplicate commit while pending, preserve drafts/selections on recoverable failures, expose Retry, retain usable cache during refresh. Only a successful response can yield an empty account or completed save. Accessible loading/error announcement; focus first invalid field; no indefinite skeleton on error. Native/API tests must cover missing/late/out-of-order responses.

## Shared acceptance checklist

1. Auth: no signup session before OTP; signup/reset purposes cannot cross; safe social linking; offline session restore; pending scan/manual intent survives auth failure/cancellation/retry.
2. Scan/import: denial, interruption, no results, zero selection, mixed currencies/cycles, exact vs inferred trial dates, more-than-25 selected records, repeated free sync, additional inboxes, repeated import, expired temporary owner and failed save. Ready uses saved IDs.
3. Home/List: all eight group counts, search + multiple statuses, zero-count selection, global vs matching totals, no sort/chip regressions, true empty vs failed fetch, cache refresh, tracking vs Active, free-trial spend exclusion.
4. Calendar/schedule: today/+7 boundary, timezone/DST, leap day, month-end anchors, quarterly/yearly, mixed event dates, empty/one/many routing, stale month response and back preservation.
5. Trial/payment/reminders: On/Off end transition, one first charge, no auto Paid, receipt ambiguity/not-found, duplicate confirmation, no schedule double advancement, cancelled/date-edited stale jobs, sent-history retention.
6. Native UX: shared dropdowns/info disclosure/status dialog, focus/keyboard, screen reader labels, Larger Text, safe areas, Reduced Motion, phone sizes and exact source/email identity.

Model/filter tests exercise the HTML helpers only. Browser approval and a green helper test do not verify production workers, native layouts, live OAuth, Firebase or purchases.

## Trial, payment and reminder persistence

Deduplicate each event + offset/send time, skip elapsed offsets, and keep sent Alerts history immutable. Push permission/token management remains the existing notification contract. Trial reminders are part of normal manual tracking/reminders; additional Gmail scans are free in v1 and still require valid consent/ownership.

The immediate work is React Native frontend, section by section, with development mock operations shaped like backend responses. ### NOMW coding reference

Read-only reference inspected: local `nomw/src/screens/Help/index.jsx`, `index.function.js`, `index.style.js`, `components/CustomText/index.js`, `redux/actions/dashboard-action.js`, `redux/slices/dashboard-slice.js` and the file inventory. Observed: separate presentation/functional/style modules, shared controls, thunk → request handler → service → reducers, snake_case state/data mixed with camelCase functions/library identifiers. It is not perfectly consistent; Renewless adopts the consistent convention below rather than inheriting exceptions, raw dimensions or project-specific financial logic.

| Concern | Renewless convention |

| Screen/component/type | PascalCase, e.g. `Onboarding`, `SubscriptionCard`, `SubscriptionDto` |
| Screen modules | `index.tsx`, `index.function.ts` exporting `useOnboarding` when logic warrants separation; retain current `styles.ts` |

Keep request/mutation logic in actions/services, typed selectors and lifecycle in functional hooks, rendering in screen modules, and pure projection/validation in domain helpers. Reuse the existing request wrapper, extending it for the required cancellation/error/identity contract instead of creating a parallel networking framework. Existing components are preferred over importing NOMW components or installing its dependencies.

### Mock data, service boundary and scenarios

- **Dataset owner:** proposed `src/config/mock-data.ts` exports typed seed entities, response/scenario definitions and an explicit reference local date/timezone. Current `src/config/api.ts` remains environment/transport configuration, not the fixture dump. Fixture authoring follows the approved target model, not the obsolete three-status client types. Shapes are provisional pending backend agreement; do not claim discovered endpoints or server compliance.
- **Service selection:** one composition point selects mock or real adapters against the same typed operation interface. Development mock mode must be explicitly enabled and excluded from production startup. Never catch a failed live request and silently supply a fixture. Screens consume actions/selectors, never `MOCK_*` arrays or a second inline dataset.
- **Flow:** screen/hook → existing action → selected typed service → reducer/entity/query state → UI. Both adapters return the same success/error contract, stable IDs/revisions, request context and cursor metadata. Transport-specific envelopes are normalized at this boundary. Avoid inventing one universal response envelope unless backend agreement establishes it.
- **Coherent repository:** seed stable accounts/platform/subscription IDs, source emails/connectors, local dates, trial/renewal/access events, reminders, sent Alerts, Gmail receipt evidence and related payment rows. Home/Calendar/List/History/Payments/platform/inbox views must refer to the same records. Use exact decimal/minor-unit money under the agreed contract, no cross-currency sum; test currency-specific precision. Reference date makes fixtures reproducible and is injectable only in development, never shown as current production truth.
- **Mutations:** clone seed data into an isolated in-memory mock repository, never mutate exported config. Create/Edit/Cancel/Track again/Delete/import update owned entities/revisions and invalidate projections just as real operations will. An idempotent retry cannot create duplicates. Reset restores the seed and clears mock session/drafts/query state; account changes cannot leak data. Mock state is transient by default, not silently stored in production MMKV.
- **Scenarios:** populated, initial pending, refresh with data, true empty, filtered empty, network/server failure, field error, permission/authorization failure, conflict and retry. Configure bounded latency/failure in the adapter, not in the UI. Only the mock adapter may simulate scan/AI job stages; production completion always depends on owned server results. Scenario controls are development tooling outside the approved product UI.
- **Auth/providers/media:** development credentials/session/OTP are clearly mocked and kept separate from production storage and live connectors. Simulated Google/Apple/Gmail/push/voice/extraction outcomes are not integration proof. Use synthetic receipt/statement/media references without personal data. File picking/recording/preview adapters can be implemented and tested separately; synthetic extraction remains visibly disclosed in development tooling, not new debug copy inside locked screens.
- **Coverage:** seeded scenarios exercise multiple subscriptions on one platform, multiple inboxes, all derived groups, no date, due today, trial On/Off and ended, cancellation/access expiry, month-end and multiple currencies. Actually-sent Alerts and Gmail successful-receipt Payments remain distinct from expected events. Derived transitions must not invent Paid/Expired proof.
